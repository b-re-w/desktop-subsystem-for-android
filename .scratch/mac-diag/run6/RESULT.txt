WHAT THIS SAYS
- In about 4 hours of KASAN run time with swap and reclaim active, no slab, page, stack or
  vmalloc use-after-free and no out-of-bounds access was seen. If the corruption came from
  kernel code touching freed or foreign memory through a checked access, KASAN would very
  likely have reported at least once.
- The one crash is again a pointer field that reads as 0 in an object that is in use. The
  earlier panics have the same shape: run5 Z1 (vmalloc PTE 0 in packet_rcv), run5 K2
  (anon_vma_name NULL), run5 C3 (rss counter), run3 (rb-tree and list nodes). So the picture
  is "memory in use loses its content" rather than "a stale pointer is used". My reading,
  not proven: something clears or replaces page contents outside the checked accesses
  (the host side of the VM, a device, or page contents lost on the reclaim/swap path).
- It is also possible that the boot5 crash is a separate bug in the 6.18 futex private hash
  code. One sample cannot tell.
- Rate: 1 of 16 here versus 5 of 18 for the shipped kernel with reclaim and swap (run3-5).
  Fisher p about 0.18: not a significant drop. KASAN timing and MGLRU off both differ, so
  this does not say MGLRU is involved.
- Looked at the DSA kernel patches that touch memory: page-reporting-rereport,
  -taken-clusters, -no-delay, dsa-host-memory. Nothing wrong found by reading. On the Mac
  page reporting reports nothing (reported_total_kb = 0 in run5), so rereport is most likely
  a no-op there; part 1 would confirm it.

DOES IT AFFECT WINDOWS
- Not known, because the cause is not found. The guest kernel, the init reclaim sequence and
  dsa-channeld's trims are the same on Windows, so a guest-side bug in that path would hit
  Windows too. The evidence here leans to memory content being lost outside the kernel's own
  checked accesses, which would be specific to how the host backs guest memory
  (Virtualization.framework here, Hyper-V on Windows) and then need not affect Windows.
  Whether Windows shows the same panics with the same image is the direct check.
